# omo-routing

[English](README.md)

`/routing`을 추가하는 Senpi/OMO 확장입니다. omo TUI 안의 대화형 편집기로
`~/.omo/omo.jsonc`의 메인 세션·카테고리·에이전트 모델 체인을, 설치된 OMO 내장
기본값 위에 현재 프로필, 지정한 프로필, 또는 base 기준으로 보여 주고 고칩니다.
사용자 설정 파일이 없어도 동작합니다. 편집기는 실행 중인 세션에 연결되지 않은
프로바이더의 후보를 숨기며, 자격증명은 읽지 않습니다.

## 사용법

```
/routing             현재 프로필 레이어, Tab으로 base (프로필이 없으면 base만)
/routing -p <name>   해당 프로필 레이어 (--profile <name> 도 동일)
/routing --base      base만, 프로필 오버레이 없음
```

현재 프로필은 `OMO_PROFILE` → `OCX_PROFILE` → `OPENCODE_CONFIG_DIR` 끝 부분
순으로 정합니다("설정 해석" 참고). `/routing edit ...`은 이전 이름으로 부르는
같은 명령입니다. 존재하지 않는 프로필 이름은 사용 가능한 프로필 목록을 담은
오류가 되고, 그 밖의 인자는 옵션을 알려 주는 오류가 됩니다.

`/routing`은 omo TUI에서 오버레이(`ctx.ui.custom`)를 엽니다. 그 밖의 환경에서는
오류가 납니다. 모든 변경은 고르기만으로 하며, 카테고리 이름이나 모델 ID를
입력하지 않습니다.

목록에는 설치된 OMO 빌드의 모든 라우팅 노드가 나옵니다. 선택된 메인 프로필
(`model_profile`이 없거나 모델을 직접 고정하면 읽기 전용)과, 내장이거나 base
또는 프로필에서 설정한 모든 카테고리·에이전트입니다. OMO 릴리즈에서 새로
생긴 카테고리는 이 확장을 고치지 않아도 나타나고, `implementer` 같은 사용자
정의 노드도 나옵니다. 오버레이는 테두리로 둘러싸이고 제목은 위쪽 테두리에
표시됩니다. 테두리는 매 화면마다 현재 너비에 맞춰 다시 그리므로 터미널 크기를
바꿔도 깨지지 않습니다(20열 또는 10행보다 작으면 테두리 없이 표시). 각 행에는
노드가 무엇을 하는지(설정 또는 내장 설명의 첫 문장, 마크다운 강조 제거)를 체인
열이 36열 이상 남을 때 별도 열로 보여 주며, 선택한 노드의 설명은 상세 영역에
항상 나옵니다. 각 행은 편집 중인 레이어 기준의 상태 단어도 보입니다:

- `빌트인`: 어느 레이어도 체인을 정하지 않아 OMO 내장이 적용되며, OMO 업데이트를
  따라갑니다.
- `base`: 프로필을 편집 중이고 base만 체인을 정합니다.
- `커스텀`: 편집 중인 레이어가 자체 체인을 정합니다.
- `비활성`: `disable: true`가 적용됩니다.
- `없음`: 어디에도 체인이 없습니다.

배지: `NEW`, `변경됨`, `제거됨`은 마지막 확인 이후의 내장 변경, `*`는 저장
안 된 편집, `⚠`는 경고입니다. 경고는 연결된 프로바이더 목록에 없는 모델,
effort만 다른 같은 모델이 연달아 있는 단계(한도가 계정 단위라 폴백 효과가
없음), 연결된 후보가 하나도 없는 경우입니다.

헤더는 다음 경우에도 경고합니다: 환경변수가 가리키는 프로필이 omo.jsonc에
없을 때(대신 base를 편집), 내장 테이블을 읽지 못했을 때(그 노드는 설정된
체인만 표시), 세션 작업 디렉터리나 그 상위 디렉터리(홈 디렉터리 직전까지)의
`.omo/omo.jsonc`(없으면 `omo.json`)가 라우팅을 정하거나 읽히지 않을 때. OMO는
그런 파일을 `~/.omo/omo.jsonc` 위에 병합하므로 편집기에 보이는 내용을 덮어쓸 수
있습니다.

행의 체인과 목록 아래 상세 영역(설명, 이 OMO 버전의 내장 체인, 바뀌었으면 이전
내장 체인, base·프로필 오버라이드, 유효 체인, 경고)은 이 세션이 실행할 수 있는
후보만 보여 줍니다. 연결된 프로바이더는 OMO가 내장 단계를 거를 때 쓰는 것과
같은 `ctx.modelRegistry.getAvailable()`에서 읽습니다. 연결되지 않은
프로바이더의 단계는 `+N 숨김` 개수만 남기고 숨기며, 내장 프로바이더 그룹은
연결된 프로바이더만 남깁니다. `h`를 누르면 숨긴 단계를 `(미연결)` 표시와 함께
보여 줍니다. 레지스트리를 읽지 못하면 아무것도 숨기지 않고 그 사실을
알리며, 새 모델은 고를 수 없습니다(삭제·순서·effort 변경은 가능).

| 화면 | 키 (하단에도 표시) |
| --- | --- |
| 목록 | ↑↓ PgUp PgDn Home End 이동 · Enter/→ 체인 열기 · `r` 기본값 따르기(이 레이어의 체인 제거) · `x` 비활성 전환 · `u` 이 노드 편집 취소 · `h` 미연결 후보 · Tab base ↔ 프로필 · `c` 내장 변경 확인 처리 · `p` 프로필 메뉴 · `s` 저장 · `q`/Esc 닫기 |
| 프로필 메뉴 | ↑↓ PgUp PgDn Home End · `+ 새 프로필 저장`에서 Enter/→ 이름 입력, 프로필에서는 적용 확인 · Esc/←/`q`/`p` 뒤로 |
| 적용 확인 | ↑↓ Home End 취소/적용 선택 · Enter 확정 · Esc/←/`q` 메뉴로 |
| 프로필 이름 | 이름 입력 · Backspace · Enter 저장 · Esc 메뉴로 |
| 체인 | ↑↓ 이동 · `a` 커서 다음에 추가(`+ 모델 추가`에서 Enter도) · Enter 모델 교체 · `e` effort · `d`/Delete/Backspace 삭제 · `K`/`J` 또는 Shift+↑/↓ 이동 · `b` 내장 체인 복사 · `r` 기본값 따르기 · `x` 비활성 · `h` 미연결 후보 · `u` 취소 · `s` 저장 · Esc/←/`q` 뒤로 |
| 모델 선택 | 글자 입력으로 필터(모든 단어가 프로바이더·ID·이름에 있어야 함) · Backspace · ↑↓ · Enter 선택 · Esc 취소 |
| effort | ↑↓ · Enter · Esc; `(없음)`은 `:effort` 접미사를 붙이지 않음 |

모델 선택에는 연결된 모델만 나옵니다. effort 목록은 설치된 OMO가 쓰는 pi-ai
(omo-ai 아래에 있거나, bun 전역 설치에서는 그 옆으로 끌어올려진 사본)의
`getSupportedThinkingLevels`로 정하고, 그것을 불러오지 못하면 모델
메타데이터로 정합니다. 새 단계는 모델이 `high`를 지원하면 `high`로
시작합니다. 같은 후보(모델과 effort)는 두 번 추가되지 않습니다. effort만 다른
같은 모델은 추가할 수 있으며, 연달아 있으면 `⚠`로 표시합니다.

편집 중인 레이어에 체인이 없는 노드는 물려받는 체인(base, 다음으로 OMO 내장)에서
숨긴 단계를 뺀 모습으로 보이며, 처음 바꾸는 순간 그 레이어의 자체 체인이 됩니다.
`r`(기본값 따르기)은 반대로 그 레이어의 체인을 지워 노드가 base나 OMO 내장을
따르게 합니다. 이후 OMO 업데이트도 따라가며, 복사한 체인(`b`)은 따라가지
않습니다. 내장이 없는 노드는 마지막 모델을 지울 수 없습니다.
`r`과 `x`는 서로 독립적입니다. 기본값 따르기는 체인만 지우고 `disable`은
그대로 두며, `disable`을 바꿔도 체인은 남습니다.

### 표시 축약

체인은 표시 전용 축약으로 보여 줍니다. 프로바이더 범례: `codex` =
`chatgpt-subscription` 또는 `openai-codex`, `claude` = `anthropic-subscription`
또는 `claude-sdk-oauth`(OMO가 2026-09에 구독 프로바이더 이름을 바꿈), `gh` =
`github-copilot`. `devin`을 포함한 나머지는 그대로 표시합니다. 노력 수준 범례:
`X` = max, `E` = xhigh, `H` = high, `M` = medium, `L` = low, `O` = off 또는 none,
`mi` = minimal, `au` = auto. 마지막 `:effort` 접미사만 줄이며, `swe-2-high` 같은
모델 이름과 알 수 없는 프로바이더/노력 수준 값은 원문을 보존합니다. 저장되는
값은 언제나 정식 `provider/model[:effort]`입니다.
`{provider-a|provider-b}/model`은 하나의 내장 단계 안의 프로바이더 대안이며,
별개의 재시도 단계가 아닙니다.

### 저장

편집은 레이어별로 모아 두었다가 `s`를 눌러야 씁니다. 저장하지 않은 편집이
있으면 닫을 때 한 번 묻습니다. 저장은 모아 둔 편집을 omo.jsonc 텍스트에
바이트 오프셋 단위로 적용합니다. 주석, 키 순서, 건드린 값의 인라인/여러 줄
스타일이 보존되고, 새 항목은 주변 들여쓰기를 따릅니다.

- 체인은 그 레이어에서 OMO가 적용하는 harness 섹션에 `models`로 씁니다:
  `[native]`, 없고 레거시 `[senpi]`만 있으면 `[senpi]`, 둘 다 없는데 레이어
  루트에 이미 라우팅 키가 있으면 루트, 그 밖에는 새 `[native]`. 그 노드의
  `model`과 `fallback_models`는 레이어에서 지워 보이는 체인과 정확히 같게 합니다.
- 기본값 따르기는 그 노드의 `model`, `models`, `fallback_models`를 레이어에서
  지우고, `description` 같은 다른 키는 남기며, 비게 된 항목은 지웁니다.
- 비활성 전환은 `disable`을 쓰거나 지웁니다(base가 비활성화한 노드를 프로필에서
  다시 켜면 `disable: false`를 씁니다).

지운 항목이나 키 옆의 주석을 포함해 주석은 제자리에 남습니다. 결과는 다시
파싱되어야 하며, 이번 편집 세션의 첫 저장 직전 파일이 `omo.jsonc.bak`으로
남고(같은 세션의 이후 저장은 그 사본을 유지), omo.jsonc가 없으면 새로 만듭니다.
편집기를 연 뒤 파일이 디스크에서 바뀌었다면 첫 `s`는 경고만 하고, 두 번째 `s`가
바뀐 파일 위에 편집을 적용합니다. OMO는 omo.jsonc를 감시하다가 바뀌면 다시
불러옵니다(hot reload). 다시 불러오면 편집기가 닫히고 저장 안 된 편집이
사라지므로, 편집기가 열려 있는 동안은 다시 불러오기를 막고(OMO가
`Hot-reload deferred: the /routing editor is open; ...`을 표시), 닫는 즉시 저장한
변경이 적용됩니다. OMO의 hot reload를 꺼 두었다면 `/reload`로 적용합니다. 닫을 때
알림으로 안내합니다.

### 새 프로필로 저장

`p`는 프로필 메뉴를 엽니다. 맨 위가 `+ 새 프로필 저장`이고 그 아래에 기존
프로필이 나옵니다. 첫 줄에서 Enter를 누르면 이름을 묻고, 기존 프로필에서
Enter를 누르면 적용할지 묻습니다(아래 참고). 이름은
앞뒤 공백을 잘라낸 뒤 검사합니다. 비어 있지 않아야 하고, 기존 프로필과 정확히
같은 키면 안 되며, 공백·제어 문자·`/`·`\`를 넣을 수 없고, `__proto__`나
`[native]` 같은 예약 키도 안 됩니다. `profiles`가 객체가 아니면 거부합니다.

새 프로필의 `[native]`에는 편집기를 연 기준 프로필(현재 프로필, `-p`로 지정한
프로필, 또는 base만)의 유효 결과로 편집기가 보여 주는 설정된 라우팅이 들어갑니다.
Tab으로 base를 편집 중이어도 마찬가지입니다. 저장 안 된 편집도 포함하며, 병합된 설정의
`model_profile`, `model_profiles`, `categories`, `agents`를 그대로 복사합니다.
미연결 프로바이더의 단계와 `description` 같은 키도 함께 복사됩니다. 내장
체인은 복사하지 않으므로, 설정된 체인이 없는 노드는 계속 OMO 내장을 따르고
이후 OMO 업데이트도 따라갑니다. 결과가 비어 있어도 base와 내장을 그대로 따르는
유효한 프로필입니다. 프로필 오버레이는 base에 있는 설정을 지울 수 없으므로,
보이는 라우팅과 정확히 같게 풀리지 않는 스냅샷(예: base가 체인을 가진 노드에
대해 모아 둔 기본값 따르기)은 처음 다른 경로를 알려 주며 거부됩니다. 그
편집을 base에 먼저 저장하거나 `u`로 취소하세요.

새 프로필만 씁니다. base, 원본 프로필, 모아 둔 편집은 그대로이므로 `s`는
여전히 그 편집을 원래 레이어에 저장합니다. 쓰기 규칙은 편집기 저장과 같습니다.
주석과 형식을 유지하고, 세션의 첫 쓰기는 `omo.jsonc.bak`을 남기며, 편집기를 연
뒤 파일이 디스크에서 바뀌었다면 첫 Enter는 경고만 하고 두 번째 Enter가 바뀜
파일에 프로필을 추가합니다(다른 키는 취소). 그러면 메뉴에 새 프로필이 나타나고,
닫을 때 알림에도 그 이름이 나옵니다. 저장만으로 활성화되지는 않습니다. 직접
적용하기 전까지 활성 프로필은 그대로입니다.

### 프로필 적용

`p` 메뉴에서 기존 프로필에 Enter를 누르면 현재 활성 프로필과 적용할 프로필을
보여 주는 확인 화면이 열립니다. ↑↓로 취소나 적용을 고르고 Enter를 누르세요.
Esc는 메뉴로 돌아갑니다. 취소하면 편집 내용과 환경은 그대로입니다. 저장 안 된
편집이 있으면 취소가 미리 선택되고, 적용 줄에 버려질 편집 수가 나옵니다. 그
편집은 파일에 쓰지 않고 버립니다.

적용하면 `OMO_PROFILE`을 그 프로필로 바꾸고 편집기를 닫은 뒤 OMO에 세션을
제자리에서 다시 불러오라고 요청합니다. 프로세스 재시작이 아니라 프로필 적용과
다시 불러오기이며, 의도한 선택입니다. 대화, 작업 디렉터리, 현재 세션의 메인
모델은 그대로이고 OMO가 선택한 프로필의 설정을 다시 읽습니다. 프로필의 `model_profile`은
OMO가 그 값을 읽는 곳에서 반영되며, 이 세션이 이미 쓰고 있는 모델을 바꾸지는
않습니다.

호스트가 실제로 다시 불러온 경우만 적용으로 칩니다. 현재 파일에서 프로필이
없거나 안전하지 않을 때, 호스트에 reload API가 없을 때, 다시 불러오기가 거부되거나
미뤄질 때(응답이나 압축 진행 중, 다른 확장), 또는 기존 실행 상태를 해제하기 전에 실패할 때는 `OMO_PROFILE`을
이전 값으로 되돌리고, 저장 안 된 편집을 그대로 둔 채 이유를 알리며 편집기를 다시
엽니다.
호스트가 기존 실행 상태를 해제한 뒤 실패하면 오류를 그대로 알립니다.
이때는 기존 편집기를 복구할 수 없어 선택한 프로필을 유지합니다.

### 내장 변경

편집기는 마지막으로 확인한 내장 라우팅을 `~/.omo/routing-builtin-snapshot.json`에
둡니다. 처음 열 때 설치된 빌드를 조용히 기록하고, 이후에도 스냅샷에 없는
섹션(전에 읽지 못한 섹션)은 열 때 같은 방식으로 기록합니다. OMO를 업데이트한
뒤에는 헤더, 배지, 상세 영역에 새로 생긴 노드, 바뀐 노드(이전·현재 체인), 빠진
노드를 보여 주고, 바뀐 내장을 가리고 있는 내 체인을 표시합니다. `c`를 누르면
설치된 빌드가 새 기준이 됩니다. 읽지 못한 내장 섹션은 비교하지도, 덮어쓰지도
않습니다.

## 설정 해석

설정 오버레이는 `omo-task.js`의 규칙을 따릅니다:

- 프로필 이름: `OMO_PROFILE` → `OCX_PROFILE` → `OPENCODE_CONFIG_DIR` 이
  `profiles/<name>` 으로 끝날 때 그 basename.
- 레이어 병합 순서: base → `[native]` → `profiles.<name>` base →
  `profiles.<name>.[native]`. 객체는 깊은 병합, 배열과 스칼라는 교체.
  `[senpi]` 는 `[native]` 의 레거시 이름입니다. OMO 가 로드 시 이름을 바꾸므로
  레이어의 `[senpi]` 는 그 레이어에 `[native]` 가 없을 때만 적용되고, 있으면
  무시됩니다. `[opencode]`, `[codex]`, `[omo]` 는 여기서 적용되지 않습니다.
- `omo.jsonc` 의 주석(`//`, `/* */`)은 파싱 전에 제거됩니다. `.jsonc` 가
  없으면 `omo.json` 을 사용합니다.
- 카테고리의 비어 있지 않은 `models`는 `model`보다 우선합니다. 그렇지 않으면
  `model`과 `fallback_models`를 적용합니다. 명시적 우선 모델이 없으면 내장
  우선 모델, 설정된 폴백, 내장 단계 순입니다. 에이전트는 `model` 다음에
  `models`를 두고, 이후 상속된 카테고리/내장 폴백을 사용할 수 있습니다.
  메타데이터만 있거나 빈 카테고리/에이전트 오버라이드는 기본값을 유지합니다.
- 사용자 `model_profiles.<name>`은 모델이 비어 있어도 내장 프로필 전체를
  대체합니다. `model_profile`에 `provider/model`을 직접 지정할 수도 있습니다.

내장 기본값은 호스트 런처의 `OMO_BIN`을 기준으로
`../plugin/extensions/omo-task.js`(카테고리, 에이전트, 카테고리 상속)와
`omo.js`(메인 모델 프로필)에서 찾습니다. OMO는 이 테이블도, 이를 해석하는
함수도 export하지 않으므로, omo-ai가 직접 설치한 `@babel/parser`(설치 루트
기준으로 찾음)로 번들을 파싱합니다. 축약된 문법(`!0`, `void 0`, 펼침, 따옴표)은
직접 만든 토크나이저가 아니라 JS 파서가 읽습니다. 테이블은 축약된 변수 이름,
필드 순서, 카테고리 이름이 아니라 AST 형태로 인식합니다. 상수 데이터(리터럴,
그에 대한 연산자, 배열, 일반 객체)만 별도 `vm` 컨텍스트에서 평가하며, 함수 호출,
함수, 그 밖의 참조는 평가 전에 거부합니다. 번들을 import하거나 실행하지
않으며, 확장에 모델 목록을 복사하지 않습니다. 단계에 펼쳐 넣은 공유 프로바이더
목록(`providers:[...a8]`)은 같은 번들 안의 배열 리터럴 `a8=[...]`에서 읽으며,
그런 리터럴이 없거나 서로 다른 것이 여럿이면 지원하지 않는 것으로 처리합니다.
결과는 번들 내용이 바뀔 때까지 캐시합니다. 파일 누락, 파서 누락, 지원하지 않는
표현식, 모호한 테이블은 해당 섹션의 경고로 표시합니다.
OMO 업그레이드 후에는 소스 파일과 실행 중인 호스트가 일치하도록
호스트를 재시작하거나 다시 로드하세요.

## 설치

클론할 필요 없이 파일 하나를 OMO 확장 디렉터리로 받으면 됩니다.

```sh
# *nix / Git Bash
mkdir -p ~/.omo/agent/extensions && curl -fsSL https://raw.githubusercontent.com/yjacket/omo-routing/master/extension/routing.ts -o ~/.omo/agent/extensions/routing.ts
```
```powershell
# Windows
New-Item -Force -ItemType Directory "$HOME\.omo\agent\extensions" | Out-Null; iwr https://raw.githubusercontent.com/yjacket/omo-routing/master/extension/routing.ts -OutFile "$HOME\.omo\agent\extensions\routing.ts"
```

클론한 상태라면 `cp extension/routing.ts ~/.omo/agent/extensions/`.

그 뒤 실행 중인 세션에서 `/reload` (또는 재시작) 하고 `/routing` 을
실행하세요.

## 테스트

```sh
node --test
```

Node ≥ 22.6 필요: 테스트는 `.mjs` 이며 Node 내장 타입 스트리핑으로
`extension/routing.ts` 를 직접 import 합니다. 가짜 `pi`/`ctx` 하네스가 명령
레지스트리, `ui.custom`, 모델 레지스트리, 픽스처 `omo.jsonc` 가 든 임시
`$HOME` 을 제공합니다. senpi 도, LLM 호출도 없습니다. 픽스처 설치본은
`OMO_BIN` 이 가리키는 omo-ai 설치본의 `@babel/parser` 를 빌려 쓰므로 테스트는
omo 안에서 실행하세요(또는 `OMO_BIN` 을 지정). 테스트 하나는 그 설치본의 번들
자체를 읽으므로, 번들 형태를 바꾸는 OMO 업그레이드가 있으면 실패합니다.

## 한계

- 편집기가 후보를 숨기고 고를 수 있게 하려고 읽는 세션의 연결된 모델 목록
  (`ctx.modelRegistry.getAvailable()`) 말고는 실제 프로바이더 상태를 확인하지
  않습니다: `auth.json` 자격증명도, `credential-pool-state.json` 백오프도 읽지
  않습니다. 내장 모델/프로바이더 ID는 레지스트리 별칭 정규화 전 OMO 선언을
  그대로 사용합니다. 세션/CLI 모델 오버라이드나 런타임 재시도 필터링은 보여 주지
  않습니다.
- 내장 기본값에는 `OMO_BIN`, omo-ai와 함께 설치된 `@babel/parser`, 인식
  가능한 테이블 형태가 필요합니다. 단독 Senpi나 호환되지 않는 향후 번들에서는
  기본값을 추측하지 않고 해당 섹션의 경고와 설정된 체인만 표시합니다.
- omo.jsonc 쓰기는 편집기의 저장뿐입니다. `s`는 바꾼 노드의 `model`, `models`,
  `fallback_models`, `disable`과 그로 인해 비게 된 항목만 건드리고, 새 프로필
  저장은 `profiles.<이름>`만 추가합니다. 편집기는
  `~/.omo/routing-builtin-snapshot.json`도 씁니다. 프로바이더 상태는 절대
  건드리지 않습니다. 프로필 적용은 파일에 아무것도 쓰지 않고, 이 프로세스의
  `OMO_PROFILE`만 바꾼 뒤 다시 불러옵니다.
